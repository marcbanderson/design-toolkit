# How <name> judges design

Last updated: <date>

**This file starts empty on purpose.** It is the one part of the toolkit that
cannot be inherited. The skills carry methods, which are the same everywhere.
This carries a specific designer's criteria, which are not.

A file like this is worth more than every skill beside it, and it takes a few
weeks of real work to build. Do not seed it with guesses.

---

## What it is for

A working file, not a diary. Each entry is **predictive**: when you hit the
situation described, this is what the designer will want, and why. It exists so
work comes back right the first time instead of being proposed and corrected.

The test for an entry: **would knowing this have changed what I did?** If not,
it belongs in the project's decision log or nowhere. A completed task is not a
judgment. A criterion revealed by a correction is.

## How to build it

Capture from three moments, in order of value:

1. **They corrected you.** The correction names a criterion you did not have.
   This is the richest source by a wide margin, and the only one that is
   unambiguous.
2. **They chose between options you offered.** What they picked, and more
   usefully what they passed over, is a criterion in action.
3. **They accepted without comment something they had previously flagged.** That
   is a rule now held, worth recording as settled so it stops being re-litigated.

Mark every entry **Stated** (their words, quoted) or **Observed** (inferred from
repeated choices). Never promote an Observed to a Stated. Quoting them verbatim
matters more than summarising them well, because the phrasing carries the
criterion.

Merge into an existing entry rather than adding a near-duplicate. This file
should get sharper over time, not longer. If it is growing faster than it is
being merged, it has become a diary.

## Suggested headings

Delete what does not apply. These are the categories that tend to fill up.

### How they read a screen
What they notice first, and what reads as a defect to them. Designers differ
sharply here and it is worth learning early, because it tells you what to check
before showing them anything.

### How they decide
Which questions get answered on principle and which get answered on business
need. Whether they want the structural cause or the direct fix. Whether an
option they reject should be removed or merely discouraged.

### How they want to work
Whether they want options up front or context first and direction later.
Whether feedback arrives as specification or as annotated screenshots. How much
they want to see before committing.

### What they count as done
Where a change has to exist before it is real. What has to be verified against
what. Whether they want gaps named or would rather you only report success.

### Accessibility and constraints
Anything that is a requirement rather than a preference. Colour vision, motion
sensitivity, a device or viewport that matters more than the others.
